# Регламент работы агента

## О проекте

Карта проекта — `docs/context.md`, подгружается сюда сама (строка ниже). Отвечая
на вопрос или беря фичу, начни с карты и открывай только нужные файлы; весь
репозиторий ради общего понимания не читай.

@docs/context.md

**Карта живёт вместе с кодом.** Изменил устройство — добавил или убрал сервис,
модуль, вкладку, сценарий, шаг студии, ADR, команду движка, файл данных,
переменную, поменял поток — поправь `docs/context.md` в том же коммите.
Структурные пропуски ловит `tools/context_gate.py` в `./check`; смысловые
(устаревшее описание, новый поток) — на тебе: перед `./finish` спроси себя,
верна ли карта после твоей задачи.

## Автономность

- Работай без вопросов: не используй plan mode и AskUserQuestion — в режиме
  dontAsk они блокируются, а не ждут ответа.
- Если sandbox или guard заблокировал операцию — НЕ ищи обход. Зафиксируй в
  итоговом отчёте: какая операция, какая причина в сообщении блока, что
  сделал вместо неё. Расширение прав (домены сети, каталоги) — решение
  человека через правку `.claude/settings.json`.
- Всё, что не заблокировано, разрешено — действуй.

## Задачи и ветки

Человек запускает голый `claude` и пишет задачу. Весь поток веток ведёшь ты,
никаких скриптов от человека не требуется.

```
main  ◀── PR (сливает человек) ──  staging  ◀── ./finish ──  ветка задачи
```

- `staging` — твоя интеграционная ветка: в неё попадает каждая готовая
  подзадача, от неё стартует следующая. Человек в неё не ходит. Если её нет,
  `./finish` создаст её от `main`; можно и самому: `git branch staging main`.
- Твои полномочия: создавать ветки, вливать их в `staging`, пушить свою ветку
  и `staging` в origin, открывать и обновлять PR `staging → main`.
- `main`/`master` не трогаешь вообще: ни коммита, ни пуша, ни перемещения
  ветки, ни `gh pr merge` — PR сливает человек. Заблокировано guard'ом,
  `pre-commit`, `pre-push` и worktree-изоляцией.
  Историю `staging` не переписывать: только fast-forward через `./finish`.

### Старт задачи

1. Если сессия в main checkout (preflight пишет об этом в контекст) — первым
   действием создай worktree инструментом EnterWorktree, имя = короткий slug
   задачи. Ветка `worktree-<slug>` создаётся от `main`.
2. Сразу `git merge staging` (если `staging` есть) — так ветка встаёт на
   результат предыдущих задач. Без этого шага `./finish` откажет.
3. Оцени объём. Одна связная задача — делай в этой ветке. Большая — разбей на
   подзадачи и запиши план в `docs/superpowers/plans/` (superpowers-цикл).

### Подзадачи

- Каждая подзадача живёт в своей ветке от `staging`: первая — в ветке
  worktree, следующие — `git switch -c <slug>/<подзадача> staging` в том же
  worktree.
- Цикл подзадачи: сделал → закоммитил (pre-commit гоняет `./check --fast`:
  гейты и линт, секунды) → `./finish` (полный `./check` с тестами, минуты).
  Скрипт пушит ветку, двигает `staging` fast-forward, пушит её и открывает
  или обновляет PR `staging → main`. Если `./finish` говорит, что `staging`
  ушла вперёд — `git merge staging` и повтори.
- Между подзадачами не останавливайся и не спрашивай — переходи к следующей.

### Финал

- Останавливайся только когда весь объём задачи выполнен или ты заблокирован.
- Итоговый отчёт человеку: что сделано, что проверено, что заблокировано,
  ссылка на PR и просьба проверить. Слияние PR в `main` делает человек.

## Бэклог и история фич

- Бэклог — каталог `backlog/` главного checkout, **вне git** (в .gitignore):
  один на все ветки и worktree, правки не коммитятся. Путь из worktree:
  `"$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")/backlog"`.
- Там: `tasks/<ID>-<slug>.md` (ID вида `BE-001`), правила и индекс открытых —
  `README.md`, шаблон — `_шаблон.md`, что уже сделано — `CHANGELOG.md`.
- Перед любой задачей найди её в `backlog/tasks/` и `backlog/CHANGELOG.md`.
  `сделано` — не делай заново; `отменено` — не делай, причина в файле.
  Задачи нет — заведи файл по шаблону, потом работай.
- Писать в `backlog/` можно только из главного checkout: из worktree-сессии
  запись туда блокируется (sandbox и изоляция Edit), читать — можно.
  Поэтому: найди/заведи задачу и поставь `статус: в работе` ДО `EnterWorktree`;
  после `./finish` — `ExitWorktree` (keep) и закрой задачу: `статус: сделано`,
  `сделано: <дата>`, `pr: <номер PR без #>` (или sha), раздел `## Решение`.
  Новые задачи, найденные по ходу, копи в отчёте и заводи там же, в конце.
- ID задачи — в сообщении коммита.
- Индекс и журнал собирает `tools/tasks_gate.py` (зовётся из `./check`, можно
  вручную) — руками не правь; бэклог не по правилам `./check` не пропустит.

## Коммиты

- Формат: `тип(область): описание`. Типы: `feat fix docs refactor test chore
  build ci perf style`. Сабж ≤72 символов, тело — ёмкое, без воды.
- Строку соавторства НЕ добавляй (`Co-Authored-By`, `Generated with…`) —
  commit-msg-хук отклонит.
- Pre-commit сам гоняет `./check --fast`; тесты затронутого сервиса перед
  коммитом запускай точечно (`make test T="-k montage"`), полный прогон —
  `./finish`. Хуки не обходить (`--no-verify` заблокирован guard'ом).
- На новой машине хуки включаются один раз: `sh bootstrap.sh`.

## Текст для озвучки

Пишешь текст, который пойдёт в синтез речи (статья, выпуск, сценарий видео,
перевод «чтобы сгенерить видео»), — сначала прочитай
`app/narrator/docs/tts-guide.md` и пиши по нему. Модель озвучки читает
буквально: ссылки, код, скобки, цифры и слова капсом (EXPLAIN читается по
буквам) портят звук. Код, запросы и вывод команд в текст озвучки не попадают
никогда — только пересказ словами, что они делают. Исключение — дайджест под Gemini TTS, см.
`app/narrator/CLAUDE.md`. Промпты студии берут выжимку из `studio/prompts.py`
`TTS_RULES` — правишь гайд, поправь и её.

- Черновики и скрипты-однодневки — в scratchpad-каталог сессии или `tmp/`
  (в .gitignore). В репозиторий им нельзя.

## Документация

- Дизайн-спеки — `docs/superpowers/specs/`, планы — `docs/superpowers/plans/`
  (superpowers-цикл: brainstorm → spec → plan → execute), решения — ADR в
  `docs/decisions/`.
- У каждой спеки, плана и ADR — YAML-шапка `тип / статус / обновлено` и
  связи (`план:` у спеки, `спека:` у плана). Словари статусов и формат — в
  `docs/README.md`; `./check` не пропустит шапку не по регламенту.
- Статусы веди по ходу работы: план → `в работе` на старте, `завершено` в
  конце; спека → `реализовано`. Поле `обновлено` — дата правки.
- Индексы между `<!-- gate:begin … -->` / `<!-- gate:end … -->` собирает
  гейт — руками не правь.
- Где какие разделы: `app/platform/README.md` — только установка, запуск и
  разработка (≤200 строк, `./check` следит); пользоваться вкладками —
  `docs/user-guide.md`, настройки и переменные — `docs/configuration.md`,
  HTTP API — `docs/api.md`, аварии — `docs/runbook.md`. В README — ссылка.

## Долгие операции

- Не держи сессию на блокирующем ожидании: джоба дольше минуты (выгрузка,
  сборка датасета, внешний API с опросом) — это три отдельных вызова:
  запустил → проверил статус → забрал результат. Между ними делай другую
  работу.
- MCP-серверы с блокирующим циклом опроса внутри не подключай — вешают
  сессию. Нужен такой источник — обёртка-CLI с `trigger / status / fetch`.
- Выгрузку сырья сопровождай манифестом рядом (`<файл>.manifest.json`):
  источник, дата, входы, id джобы, число записей — чтобы её можно было
  повторить.

## Грабли

- Перед задачей в области, где уже ошибались, прочитай `docs/грабли.md`.
- Человек отклонил результат целиком, а не поправил детали — это системная
  ошибка: допиши запись в `docs/грабли.md` по шаблону и внеси предохранитель
  (правило, чек, шаблон).
- Сверка со своим брифом не заменяет проверку на пригодность: прежде чем
  сдать, спроси себя — тот ли бриф, а не только выполнен ли он.
