# 0004. Один GPU-замок на все тяжёлые модели

Записано задним числом (DX-008); выбор описан в спеке
`docs/superpowers/specs/2026-10-15-ai-platform-design.md` (подход B).

## Контекст

Фото (mflux, Flux2CLI), видео (LTX, Wan) и озвучка (narrator) — модели на
десятки гигабайт. На Mac с единой памятью две такие модели одновременно
дают OOM или своп на минуты. Раньше это были три отдельных сервиса, которые
о памяти друг друга не знали.

Альтернативы: шлюз над тремя сервисами (без координации — OOM); лимит по
свободной памяти (непредсказуем: модели раздуваются по ходу генерации).

## Решение

- Один процесс-монолит и один `Gate` (`app/platform/aiplatform/core/gate.py`):
  в памяти одна тяжёлая модель за раз, очередь FIFO, ожидание можно
  отменить.
- Воркеры вкладок (`photo/jobs.py`, `video/jobs.py`, `audio/jobs.py`) и
  задачи с `gpu=` (`core/tasks.py`) берут замок только вокруг запуска модели.
  Лёгкие шаги — LLM через CLI, ffmpeg, сеть — замок не берут.
- Шаги сценариев замок не держат: они ставят обычные задачи вкладок.
- Кто держит замок и сколько — в `/api/status` (`gpu`, `gpu_held_s`), в
  интерфейсе — «Ждёт GPU (занят: …)».

## Последствия

- Нет OOM от параллельных моделей; генерации идут строго по очереди, даже
  когда две маленькие модели поместились бы вместе.
- Зависшая модель держит всех: видно по `gpu_held_s`, лечится отменой
  задачи или перезапуском (runbook REL-015).
- Модель, запущенная вне платформы (терминал, другой сервис), замок не
  видит — возможен OOM.

## Когда пересматривать

- Появится машина с памятью, где две модели гарантированно помещаются.
- Генерация уедет на внешний GPU/облако.
- Очередь станет узким местом настолько, что нужна приоритизация, а не FIFO.
