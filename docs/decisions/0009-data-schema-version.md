# 0009. Версия схемы у файлов данных, миграции при чтении, карантин битых записей

Продолжение [0007](0007-files-not-database.md): данные — JSON-файлы в `data/`.
Здесь — как меняется их формат (BE-008).

## Контекст

У `project.json`, `job.json`, файлов задач, `published.json`, `settings.json`,
`channels.json` не было версии. Совместимость держалась на правках при
загрузке («шаг, которого не было в этой версии»). Загрузчик ловил только
`OSError`/`JSONDecodeError`: валидный JSON без `steps` или `id` давал
`KeyError` при старте и ронял весь сервис, а не один выпуск. Код после
отката не знал, что данные записаны более новой версией, и мог их испортить.

## Решение

- **Поле `schema: N`** — целое, первым полем файла. Нет поля — схема 0
  (данные до BE-008). Номер свой у каждого вида файла: `PROJECT_SCHEMA`
  (`studio/pipeline.py`), `JOB_SCHEMA` (`core/schema.py`), `TASK_SCHEMA`
  (`core/tasks.py`), `PUBLISHED_SCHEMA` (`studio/steps.py`), `SCHEMA`
  (`core/settings.py`), `CHANNELS_SCHEMA` (`studio/publish.py`). Сейчас у всех 1.
- **Списки — в обёртке.** `published.json` — `{"schema": 1, "records": [...]}`,
  `channels.json` — `{"schema": 1, "channels": [...]}`. Голый список читается
  как схема 0.
- **Миграции — при чтении**, цепочкой `migrations[v]: v → v+1`
  (`core/schema.upgrade`). Записывается всегда текущая схема. Добавить
  необязательное поле с умолчанием при чтении — не повод поднимать номер;
  номер растёт, когда старый код прочтёт новый файл неверно (переименование,
  смена типа, обязательное поле).
- **Файл новее кода не трогаем.** Запись с `schema` больше известной —
  `schema.TooNew`: выпуск или задача не грузятся, настройки и журналы
  читаются как есть, но не перезаписываются (`settings` → 409
  `schema_too_new`, каналы → 503 `config_broken`). Причина — в problems
  («записано более новой версией»).
- **Карантин.** Запись, которая не JSON или без обязательных полей
  (`core/schema.load_record`, проверки `require(...)`), переименовывается в
  `*.bad` рядом, причина — в problems и в лог (`data.quarantine`); остальные
  записи грузятся. Данные не удаляются: файл чинят руками и снимают `.bad`.

## Откат кода

- На версию с той же или большей схемой — без действий.
- На версию до BE-008 (не знает обёрток списков): перед откатом —
  `python -m aiplatform.core.schema unwrap <data>`, обёртки
  `published.json` и `channels.json` разворачиваются в списки. Без этого
  старый код увидит пустой журнал публикаций и может отправить пост
  повторно. Поле `schema` в остальных файлах старый код игнорирует.
  `channels.json` по нестандартному пути (`AIP_CHANNELS`) — развернуть
  тем же способом руками.
- На версию со схемой меньше текущей (после BE-008): она увидит
  «записано более новой версией» и ничего не перезапишет; вернуть данные
  назад — только из бэкапа (REL-012).

## Последствия

- Битый файл одного выпуска больше не роняет старт.
- Новый вид файла данных — номер схемы, `stamp`/`wrap` при записи,
  `load_record` или `upgrade` при чтении, строка в этом ADR.
- Тесты: `app/platform/tests/test_data_schema.py`.
