# Документация проекта

| Папка / файл | Что это |
|---|---|
| `superpowers/specs/` | дизайн-спеки (superpowers:brainstorming) |
| `superpowers/plans/` | планы реализации (superpowers:writing-plans) |
| `decisions/` | ADR: одно решение = контекст → решение → последствия |
| `грабли.md` | системные ошибки и предохранители от них |
| `CHANGELOG.md` | журнал версий: что вошло в каждый релиз |


Бэклог и история фич — вне git, в `backlog/` главного checkout (общий для
всех веток и worktree): правила — `backlog/README.md`, гейт —
`tools/tasks_gate.py`.

## Шапки артефактов

У каждой спеки, плана и ADR — YAML-шапка; её проверяет `tools/docs_gate.py`
(зовётся из `./check`, значит из pre-commit и `./finish`):

```yaml
---
тип: spec            # spec | plan | adr — совпадает с папкой
статус: черновик
обновлено: 2026-09-21
план: 2026-09-21-foo.md   # spec: имя плана или «нет»
---
```

| Тип | Статусы | Связи |
|---|---|---|
| spec | черновик → утверждено → реализовано; неактуально | `план:` — файл плана или `нет` |
| plan | запланировано → в работе → завершено; брошено | `спека:` — обязательно, ссылка взаимная |
| adr | предложено → принято; заменено | при `заменено` — `заменён_на:` |

Индексы в `superpowers/README.md` и `decisions/README.md` собирает гейт —
между маркерами `<!-- gate:begin … -->` / `<!-- gate:end … -->` руками не править.

## Версии

Одна версия на весь репозиторий — дата релиза: `ГГГГ.ММ.ДД`, второй и
следующие релизы за день — `ГГГГ.ММ.ДД.N` (N с 2). Тег — `v<версия>`. До
первого релиза версия `0.1.0`.

Где живёт версия (`tools/release.py` держит их одинаковыми, `./check` это
проверяет): `version` в `app/platform/pyproject.toml` и
`app/narrator/pyproject.toml`, `aiplatform.__version__` (её отдают
`/api/health` и `/api/config`, шапка страниц показывает её справа), запись
narrator в `app/narrator/uv.lock`.

Релиз — два шага, из `app/platform`:

1. `make release-prep [DATE=ГГГГ-ММ-ДД]` — в ветке задачи (агент или
   человек): поднимает версию во всех файлах и вставляет в
   [`CHANGELOG.md`](CHANGELOG.md) заголовок версии со списком задач бэклога
   из коммитов с прошлого тега. Коммит `chore(release): <версия>` едет в
   `main` через PR, как любой другой.
2. `make release-tag` — человек в `main` после слияния PR: ставит тег
   `v<версия>` на HEAD, если версия во всех файлах одна, в журнале есть её
   заголовок и тега ещё нет. Затем `git push origin v<версия>`.

Пока прошлая версия не выпущена тегом, `release-prep` следующую не готовит.
Деплой с тега и откат — REL-014.
